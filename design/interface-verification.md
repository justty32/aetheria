# 界面的一致性驗證（M4 的完成判準）

> 這份只回答一件事：**怎麼證明 L1↔L2 的界面沒有出錯。**
> 機制本身見 [interface-lifecycle.md](interface-lifecycle.md)（生命週期與補算）
> 與 [interface-world-mid.md](interface-world-mid.md)（投影與歸約）。
> 通用原則見 [principles.md](principles.md)；用詞以 [glossary.md](glossary.md) 為準。

## 為什麼這份要獨立

M1 的教訓：**十二階段的雜湊全綠、114 個測試全過，而世界是單色的。**
一個測不到真東西的通過，比失敗更危險——它看起來像進度。

所以「怎麼驗」值得和「怎麼做」分開寫，並且每一條驗收都要問：
**這條測試若在系統壞掉時仍然會通過，那它就沒有價值。**

## 一致性驗證（M4 的完成判準）

這套機制的正確性必須靠自動測試釘死，不能靠肉眼：

| 測試 | 內容 | 判準 |
|---|---|---|
| **來回不變** | `L_FULL` → `L_COARSE` → `L_ABSENT` → 重載，中間不推進時間 | 歸約量逐位元相同；持久層物件座標與狀態相同 |
| **卸載等價** | 同一 seed 跑兩份：A 全程保持 `L_FULL` 跑滿 N 旬；B 落到 `L_ABSENT` 推進 N 旬再重載。**兩份都用時鐘推進 N×864,000 秒，不要用回合數計**（stride 可變） | 兩份的 Region tile 歸約量差異 < 10%；持久層物件集合相同 |
| **命運無偏** | 具名角色在 A（玩家在場）與 B（離線補算）兩條路徑下的存活率分布 | 分布無顯著差異，見 [significance-fate.md](significance-fate.md) |
| **投影決定論** | 同一輸入投影 100 次 | 逐位元相同 |
| **公式校準** | 隨機 1000 個 Region 狀態，比對 `reduce(project(s))` 與 Region 近似公式 | 相對誤差 < 5%（見界面文件） |
| **飽和** | elapsed 給 10 旬與 10000 旬 | 後者的老化與事件數不超過上限 |
| **骨架遷移** | 人工改慢變數後重載 | 無物件遺失（保留或明確標記毀壞），無座標落在不合法格 |

「卸載等價」的 10% 是**刻意允許的誤差**，不是 bug：
Site 在場時走的是高解析度公式，不在場時走 Region 近似公式，兩者本來就不會完全相等。
重點是誤差有界、方向無偏（不會系統性地讓「常常進城」比「不進城」更划算）。

**無偏性也要測**：跑 100 次隨機的載入／卸載序列，歸約量的平均值不應顯著偏離
全程載入的基準。若玩家能靠反覆進出城刷資源，那就是設計漏洞而非誤差。


## 每條測試都要有偵測力

上表的每一條都要配一個**負向控制**：故意破壞它該抓的東西，測試必須失敗。
M2.3 的實例——三次冷往返的六點雜湊序列全同（通過），
然後刻意把持久建築 `Idle → Derelict`，序列在該斷處斷開（證明它抓得到）。

沒有負向控制的「通過」不算通過。三個反覆出現的假通過陷阱：

| 陷阱 | 症狀 | 對策 |
|---|---|---|
| 狀態沒真的離開記憶體 | 重載其實是「沿用」不是「重算」，重算路徑的 bug 全被掩蓋 | 冷載入，並**斷言該 zone 展開前確實未載入** |
| 待驗的值停在預設 | 「重載後回到預設值」既可能是正確還原也可能是被重設，無法區分 | 往返前先把值改成**非預設** |
| 只比頭尾 | 中間的漂移可能互相抵消 | **每個中間點都取值**，比整條序列 |

⚠ 還有一個更隱蔽的：**空的層必然通過。**
持久層是空的時候做往返測試，結果一定是「不漂移」，但它什麼也沒證明。
**先確認被驗的東西真的存在**，再談它有沒有漂移。
