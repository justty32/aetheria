# L3 下層地圖（Local）

> Site 的一格放大。64×64、一格約 2 m、探索 1 分鐘一回合、戰鬥 6 秒一回合。
> 開放世界式的串流探索，最直接的參考是 ToME4（`~/repo/moddings/tome4`）。
> 串流見 [lowmap-streaming.md](lowmap-streaming.md)；生成見 [localgen.md](localgen.md)。
> 通用原則見 [principles.md](principles.md)；用詞以 [glossary.md](glossary.md) 為準。

## 尺度自洽的最後一級

64 × 2 m ≈ 128 m，正好是 Site 一格（125 m）。**一格 2 m 是人身尺度**——
一個人佔一格、一扇門在兩格之間、一間 10 m 見方的房間是 5×5 格。

這一級**不再往下分層**。房屋內部、地窖、洞穴全部直接在 Local 表達：

| 東西 | 怎麼表達 |
|---|---|
| 一棟房子 | Local 上的 5×5～10×10 格 |
| 房間 | 幾格 + 牆（邊屬性） |
| 門 | 某條邊上帶可開關旗標的 `EdgeDef` |
| 地窖、地城、礦坑 | **同一個 zone 的負 z 層**，不是另一個 zone |

Site 層的「建築」佔 1～4 格 = 125～500 m，那其實是**街廓**尺度；
放大到 Local 才是一棟棟房子。這個對應關係要記牢，實作時很容易搞混。

## 資料模型

```cpp
struct LocalTiles {                      // 4096 格 × 每個 z 層
    std::vector<GroundId>  ground;       // → GroundDef 下標
    std::vector<OverlayId> overlay;      // 地毯、血跡、雜物堆
    std::vector<EntityId>  occupant;     // 佔位實體，0 = 空
    std::vector<EdgeId>    edges;        // 四邊：牆、門、柵欄、窗、懸崖
    std::vector<uint8_t>   light;        // 光照（影響視野與潛行）
};
```

**牆與門是邊屬性**，與 L1 的河流道路、L2 的城牆共用同一套 `EdgeDef` 機制
（見 [definitions.md](definitions.md)）。所以視線、尋路、開關門全部只查邊，
不必發明「半格」或「牆佔一格」這種會浪費一半地圖的表達。

`occupant` 是**單一佔位者**（一格一個實體），這是四鄰接格子制的自然結果。
道具、屍體、掉落物不佔 `occupant`，它們掛在格上的稀疏容器裡。

## 垂直層

`Zone::layers` 的鍵即 z：地面 0、地下為負、樓層為正。
**同一個 zone 內**，繼承自 medps（見 [zone-model.md](zone-model.md)）。

| z | 典型內容 |
|---|---|
| +2, +1 | 塔樓、二樓、樹冠 |
| 0 | 地面 |
| −1, −2… | 地窖、下水道、礦坑、地城 |

樓梯／坑洞是「某格的 z 方向可通行」，**不是**跨 zone 的傳送門。
這讓地城天然屬於它上方的那個 Local，載入卸載一起走，不必另外定址。

深層地城（往下十幾層）仍在同一個 zone 的 layers 裡——
若某天真的深到記憶體吃不消，那時再談拆分，現在不預先設計。

## 玩法：事件從邊緣進來

Local 是三層裡最常「被上層通知」的一層。
[event-scaling.md](event-scaling.md) 的展開規則落在這裡最具體：

> Site 層說「部隊 B 在東側進攻」→ Local 的邊界條件就是「敵方單位從東邊緣進入」。

同一套機制也處理：商隊經過、巡邏隊走來、野獸遷徙、災變波及。
**Local 從不自己決定「誰來了」**，那是上層的事。

## 持久層：更小、更短命

L3 的持久層是三層裡最小的，這直接決定了它的生命週期參數
（見 [interface-lifecycle.md](interface-lifecycle.md)）：

| 類別 | 存不存 |
|---|---|
| 玩家改變的地形（挖通的牆、燒掉的房子） | ✅ 存 |
| 開過的箱子、拿走的道具、觸發過的機關 | ✅ 存（旗標，很小） |
| 具名 NPC 的生死與位置 | ✅ 存 |
| 屍體、掉落物、血跡 | ⚠ **短期存，超時清理** |
| 地形細節、植被、無名 NPC、裝飾 | ❌ 重算 |

「屍體與掉落物超時清理」是必要的：一個玩家反覆刷的地城若永久保留每具屍體，
存檔會無限膨脹。作法是給它們一個過期時間，清理在重載時順手做。

`N`（落到 `L_ABSENT` 前的閒置旬數）**初值 1**——L3 沒什麼好留的，
下次來重生成即可，只要持久層還在，玩家不會發現差別。

## 與上層的界面

**完全複用 L1↔L2 那一套**，只是尺度降一級：

| 機制 | L1↔L2 | L2↔L3 |
|---|---|---|
| 投影 | Region tile → Site | Site tile → Local |
| 歸約 | Site → Region 的歸約量表 | Local → Site 的歸約量表 |
| 慢／快變數 | Region 的地形 vs 人口 | Site 的 ground/structure vs 佔用者、狀態 |
| 骨架穩定性 | 骨架只依賴慢變數 | 同 |
| 接邊一致性 | 角 → 邊 → 面 | **同一份實作**，`w` 換成 64、seed 換成 `site_seed` |
| 生命週期 | LOD 四級 + 場強 | 同，但 `N` 更短、半徑更小 |

**這是驗證抽象是否真的通用的地方。** 如果 L2↔L3 需要新機制，
那表示 L1↔L2 的抽象抽錯了——目前推演下來沒有需要新機制的地方，
但這要等實作撞過才算數。

L3 的歸約量表比 L2 短得多，因為 Local 能影響 Site 的東西不多：

| 歸約量 | Local 側 | Site 側 |
|---|---|---|
| 建築完整度 | 牆與結構的損毀比例 | `structure` 的狀態 |
| 佔領 | 場上控制點的歸屬 | 該格的控制方 |
| 資源產出 | 採集點的剩餘量 | 該格的產出修正 |
| 通行性 | 挖通／堵死的路徑 | 該格的通行成本 |
