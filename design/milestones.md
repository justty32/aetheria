M2 與 M4 是本專案真正的技術風險，其餘是工作量問題。

## M7 之後的判準怎麼定

⚠ **M6 之前的判準都是「機制成不成立」，M7 之後是「玩起來對不對」**——
後者沒有單一數字可斷言，所以判準要改成**可觀測的行為**，不是「做完了」。

| 里程碑 | 一句話判準 | 為什麼這樣定 |
|---|---|---|
| M7 | 三條位階來源**在同一場戰鬥裡可比**，且各自有不可替代的用法 | 若魔法只是「另一種傷害型別」，那它就不該是獨立系統 |
| M8 | **不看程式碼、不跑測試，只用滑鼠鍵盤，能打完一場仗並看到世界因此改變** | 這是唯一無法靠測試自證的判準 |
| M9 | 關掉 core 重開，畫面與音景**完全一致** | 呈現層不得持有玩法狀態（[tech-stack.md](architecture/tech-stack.md) 鐵律） |
| M9 | 同一存檔跑兩次通關，**世界雜湊在每個檢查點相同** | 決定論是可玩性的前提，不是附加價值 |

## ⚠ 為什麼 M8 從「呈現」改成「可玩迴圈」（2026-08-22 量到）

`bridge/` 目前**只對外開了四個方法**：`generate_region`、`get_core_version`、
`poll_events`、`tick_to_date`。`godot/` 只有一個 debug renderer、main、事件面板。

也就是說：**M6／M7 做的戰鬥、勢力 AI、外交、地城、湧現任務，從遊戲裡一個都碰不到。**
core 很厚，但它不是一個能玩的東西——而且**每多做一輪 core，這個缺口就更大**。

所以順序要換：**先把迴圈打通，再談美術與音效**。
沒有迴圈，美術沒有地方掛；有了迴圈，美術是換皮，音效是加層。

**待規劃清單**（見下節）就是 M7／M8 的工作項來源，不必另立。
