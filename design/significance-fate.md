# 命運判定：統計優先，具名例外

> 高層事件（饑荒、瘟疫、屠城、戰敗）如何同時做到「統計上正確」與「對玩家在乎的角色有戲」。
> 承接 [significance.md](significance.md)。
> 通用原則見 [principles.md](principles.md)；用詞以 [glossary.md](glossary.md) 為準。

## 問題

饑荒發生在某座城。玩家認識的那位雜貨店老闆娘住在那裡。

- 若只算統計：城裡死了 1200 人，老闆娘的生死沒有答案，玩家感覺不到任何事。
- 若逐一模擬每個人：十萬人各擲一次骰，成本無法接受，而且大部分結果沒人看。
- 若讓具名角色免疫：世界失去重量，玩家認識誰誰就不死。

## 三階段演算法

```
階段 1  對 Cohort 算出總量        → 這座城的平民 Cohort 損失 1200 人（12%）
階段 2  對 Cohort 內的具名成員逐一擲判 → 老闆娘：倖存 / 死亡 / 重傷 / 流離
階段 3  用階段 2 的結果回填配額     → 無名成員的損失數調整為 1200 − 具名成員的實際死亡數
```

**階段 1 永遠先跑，而且它的結果是權威的。** 這與
[interface-world-mid.md](interface-world-mid.md) 的「數值歸 Region」完全同構——
總量由高層決定，個體只是在總量之內分配。

## 階段 2：具名成員的判定

```
base_p      = Cohort 的損失率                        // 12%
adjusted_p  = base_p × Π modifier_i                  // 各項修正相乘
outcome     = roll(rng, adjusted_p)                  // 用注入的確定性 RNG
```

修正項來自角色本身，全部是**可解釋的**（能寫進敘事）：

| 修正項 | 方向 | 敘事 |
|---|---|---|
| 地位（貴族、官員） | ↓ 降低死亡率 | 「城主的糧倉先開給了自己人」 |
| 財富、存糧 | ↓ | 「她鋪子後頭還藏著半袋麥」 |
| 與玩家的關係深度 | ↓ | 玩家在乎的角色有倖存偏袒 |
| 職業風險（醫者、士兵） | ↑ 或 ↓ | 瘟疫中醫者死亡率更高 |
| 年齡、健康、特質 | ↕ | 老人與孩童在饑荒中更脆弱 |
| 所在分區 | ↕ | 貧民區的損失率高於商業區 |

**倖存偏袒是刻意的，但不是免疫。** 被 mark 的角色死亡機率明顯低於平均，
卻永遠 > 0。這是張力的來源：玩家知道她可能會死，所以會想辦法救。
偏袒係數是難度選項——硬核模式下係數趨近 1。

結果不只有生死。`outcome` 是一個分布：

```
倖存無恙 / 倖存但重傷 / 倖存但失去財產 / 流離（遷往他處）/ 死亡
```

「流離」特別有用：它讓角色離開這座城但仍活著，日後可能在別處重逢。

## 階段 3：配額守恆

> **具名成員的判定結果必須從 Cohort 的配額中扣抵。**

若 Cohort 該死 1200 人，其中具名成員實際死了 3 人，那無名成員就死 1197 人。
若具名成員全部倖存，無名成員就多死那幾個，補足 1200。

為什麼守恆是硬性要求：

1. **統計層與個體層不能有兩個真相。** 這是整份設計反覆出現的同一條原則。
2. **防刷。** 若具名角色的倖存是「額外」的，玩家就有動機去大量 mark 人來降低總損失。
   守恆讓 mark 不改變總量，只改變**誰**承受。
3. **歸約一致。** Cohort 的損失最終要歸約回 Region 的人口數字。
   兩層若不守恆，Region 的人口就會漂移。

具名成員多到足以影響配額時（例如一個 Cohort 裡有 50 個被 mark 的角色），
先算具名、再把剩餘配額分給無名。若具名成員的死亡數已超過配額，
就**不再對無名成員扣損**，並記一則「這場災難特別針對了有頭有臉的人」的敘事。

## 敘事產出

每個具名成員的判定都產生一則**事件**，這是玩家實際看到的東西：

```
[饑荒·第 3 旬]  石橋鎮
  平民損失 1197 人（12%）
  ▸ 雜貨店的瑪莎 倖存，但鋪子已空
  ▸ 老兵葛倫 死於饑荒
```

無名的部分是一行數字，具名的部分是一行故事。這正是這套機制存在的理由。

## 確定性

判定必須完全確定，否則存讀檔與回歸測試都會壞掉：

- RNG 用注入的 `mt19937_64`，種子 `hash(event_id, cohort_id, entity_uid)`
- **具名成員的擲判順序固定**（依 `entity_uid` 排序），不依賴容器迭代順序
- 腳本掛勾（自訂 modifier）受 [rules-extensibility.md](rules-extensibility.md) 的六條鐵律約束

## 離線與補算路徑

Site 被卸載期間發生的饑荒，走**完全同一套演算法**：

- 階段 1 由 Region 層算（它本來就一直在跑）
- 階段 2 在**重載時**才對具名成員補擲——因為具名成員的清單在持久層裡，
  卸載期間不需要它
- 階段 3 的配額守恆自動成立，因為階段 1 的總量早就記在 Region 上了

這意味著**「玩家在不在場」不影響角色的命運分布**——
不會出現「常常進城的玩家，他認識的人比較容易活」這種漏洞。
這條要列進 [interface-lifecycle.md](interface-lifecycle.md) 的無偏性測試。

唯一的差別是**時序**：玩家在場時，判定當下就發生並演出；玩家不在場時，
判定延後到重載，一次補完，並以「你不在的這段時間發生了這些事」的形式呈現。

## 反向：個體事件如何影響統計

上面講的是「統計 → 個體」。反方向也要能走：

- 玩家救了某位具名角色 → 該角色從死亡配額移出 → 配額轉嫁給無名成員
- 玩家開倉賑災 → 影響的是**階段 1 的 Cohort 損失率**，不是階段 2 的個體修正

**玩家的干預必須作用在階段 1**，這樣它才會如實反映到 Region 的人口數字上。
只改階段 2 的話，玩家會覺得「我救了她」但城市人口毫無變化——那是設計錯誤。

- 敘事事件的模板與 i18n
