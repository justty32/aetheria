# 獨特物件

> 世界上有幾十萬個「人」，但只有幾百個該有名字。**誰有名字、名字住在哪裡、
> 不在場時他的狀態怎麼算**——這三題的答案都指向觀察點。
>
> **⚠ 本文件是方向性的骨架，不是定案。** 使用者裁定：先把縮放機制的基礎打穩，
> 這套再慢慢展開。以下記錄已確定的結構與已知的問題，細節留待後續。
> 通用原則見 [principles.md](principles.md)；用詞以 [glossary.md](glossary.md) 為準。

## 兩種存在方式

| | 標籤型（generic） | 獨特型（unique） |
|---|---|---|
| 怎麼稱呼 | 「雜貨店老闆娘」「傭兵團團長」 | 「老人格伐」 |
| 由誰決定 | 職業 + 場所 + 少量特徵，**投影出來的** | 有名字，且名字進持久層 |
| 資料在哪 | 程序層，不存檔，重載時重算 | **登記在某個觀察點上** |
| 命運怎麼算 | 併入 Cohort 統計 | 統計優先、具名例外（[significance-fate.md](significance-fate.md)） |

絕大多數存在是標籤型。這不是省事，是刻意的：
名字很珍貴，滿地都是名字等於沒有名字。

## 什麼讓一個東西變獨特

| 來源 | 例子 |
|---|---|
| **事件影響** | 主線劇情「勇者覺醒」發生 → 勇者所在村子的老人因此有了名字 |
| **玩家 mark** | 玩家反覆光顧的店主，互動累積到門檻後自動獲得名字 |
| **天生獨特** | 傳奇物品、歷史人物、地標——由資料檔直接宣告 |

前兩者是**動態**的：世界跑著跑著，某個原本無名的存在忽然變得重要。
這是這套機制最有價值的地方——獨特性是**長出來的**，不是設計師預先列好的。

## 登記在觀察點上

> **使一個東西變獨特的那個觀察點，就是它的記錄的持有者。**

「勇者覺醒」這個劇情產生了一個子觀察點（見 [observer.md](observer.md) 的觀察點樹），
因它而獨特的人事物就登記在它身上。劇情的額外資訊裡會有這樣一條：

```
老人格伐  ·  XX 洲 XX 國 XX 村  ·  狀態：安好，年邁  ·  最後觀測：第 142 旬
```

```cpp
struct UniqueRecord {
    EntityRef  ref;            // 弱引用：{zone_key, stable_uid}，解引用可失敗
    NameId     name;           // 獨特名字（進持久層）
    Locator    where;          // 層級式位置：洲 / 國 / 聚落，人類可讀
    StatusDigest status;       // 簡要狀態（一兩句可顯示的摘要）
    Tick       last_observed;  // 最後觀測時間
};
```

### 為什麼掛在觀察點而不是掛在實體上

因為實體**可能不在記憶體裡**。老人格伐所在的村子多半是 `L_ABSENT`——
他的 zone 根本沒載入。但玩家隨時可以打開劇情面板看他過得怎麼樣。

觀察點常駐（它是 root zone 的實體，見 [zone-model.md](zone-model.md)），
所以記錄常駐。實體則是按需載入的。這正是 `EntityRef` 必須是**弱引用**、
**解引用失敗是預期結果**的理由——直接繼承自 medps 的
`zone-addressing-lifecycle-design.md` §3.7。

### `last_observed` 是快照時間，不是現在

這一欄承接了 [interface-lifecycle.md](interface-lifecycle.md) 的整套補算機制：

> **記錄裡的 `status` 是上次觀測時的樣子，不是即時狀態。**

查詢時若 `now > last_observed`，就跑一次補算把狀態推到現在
（依 Region 這段期間發生的事、依 [significance-fate.md](significance-fate.md)
的具名例外判定），然後更新 `status` 與 `last_observed`。

這與 LOD 完全一致：**沒被觀察的東西不即時更新，只在被查詢時補算。**
而且它是**惰性**的——玩家不打開面板，就一次都不必算。

## 位置：層級式而非座標

`Locator` 存的是「XX 洲 XX 國 XX 村」而不是 `(region=3, x=17, y=32)`：

- 它要**顯示給玩家看**
- 它在跨 zone 未載入時仍然有意義
- 它容許粗略（只知道「在北方某處」也是合法的定位）

但它必須能**解析回實際的 zone key**（見 [zone-addressing.md](zone-addressing.md) 的定址），
否則玩家點下去無法前往。所以 `Locator` 同時帶一個可選的精確 `ZoneKey`——
知道就填，不知道就留空並只顯示粗略描述。

「不知道確切位置」本身是有玩法價值的狀態：情報、追蹤、尋人任務都建立在它上面。

## 失去獨特性

使一個東西變獨特的觀察點消失了（劇情結束、mark 撤銷），怎麼辦？

**名字不收回。** 玩家記住的名字忽然變回「某個老人」是不可接受的體驗。
處理方式是**降級而非刪除**，與 [significance.md](significance.md) 的 mark 預算超支處理一致：

| 保留 | 放棄 |
|---|---|
| 名字（進持久層，永久） | 被個別計算的資格 |
| 最後一次的 `status` 與 `last_observed` | 持續更新 |

記錄本身要**轉移**到一個保底的持有者（root 的「已知人物」登記表），
避免隨著觀察點一起被回收。日後玩家再次接觸，就地恢復。

## 已知待解

這些是這套機制展開時必須回答的，現在只登記不解：

- **同一個對象被多個觀察點登記**（劇情與 mark 都指向老人格伐）→ 記錄要不要合併？由誰持有？
- **獨特物件的數量上限**與淘汰策略（呼應 mark 預算）
- **名字生成**：延遲生成的時機、種子、文化風格（不同國家的命名規則）
- `StatusDigest` 的實際欄位與它如何從實體狀態壓縮而來
- **獨特地點**與獨特人物、獨特物品的差異（地點不會移動，但會易主、會毀壞）
- 獨特物件之間的**關係**（誰是誰的兒子、哪把劍屬於誰）——它是一張圖，成長軸要守住
- 與 [rules-extensibility.md](rules-extensibility.md) 的介面：腳本如何宣告「讓這個變獨特」

## 為什麼先擱置

這套機制**建立在縮放機制之上**：它需要觀察點樹穩定、需要事件的主場層穩定、
需要補算路徑穩定。那些先打好，這套才有地基。

同樣的理由，[significance.md](significance.md) 的 mark 一節也刻意未定案。
兩者其實是同一件事的兩面。
