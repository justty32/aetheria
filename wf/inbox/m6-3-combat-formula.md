## 主公式

```
S'ᴀ = Sᴀ × terrain × supply × morale × command × posture
R   = S'ᴀ / S'ʙ
lossʙ = base × R^p × duration
lossᴀ = base / R^p × duration
```

`S` 來自 M6.0 的等效戰力。修正項全部是乘法、**全部來自資料檔**
（新增 `data/combat.toml`），一項都不准寫死：

| 修正 | 範圍 | 說明 |
|---|---|---|
| `terrain` | 0.6～1.5 | 防守方在丘陵、渡口、城牆後有加成 |
| `supply` | 0.3～1.1 | **權重刻意最重**——一旬涵蓋十天，斷糧比戰技重要得多 |
| `morale` | 0.5～1.3 | 也決定潰散閾值 |
| `command` | 0.8～1.5 | 指揮官的位階與特質 |
| `posture` | 0.7～1.3 | 強攻／固守／襲擾／撤退 |

補給給最重是**刻意的**：它讓大地圖的補給線成為真正的戰略要素，而不是裝飾。

## ⚠ `R^p` 是這輪最大的技術風險

`p` 初值 **1.3**（1.0 = 線性，2.0 = Lanchester 平方律，1.3 是折衷）。
`p` 是**唯一一個校準時要動的數字**，所以它必須是參數，不能被寫進近似式的係數裡。

**硬性限制**：

- **不准 `std::pow`、不准 `double`、不准任何浮點。** 跨平台必須逐位元一致。
- 用定點整數（查表／整數對數／你選，但要在回報裡說明選了什麼、為什麼）
- **`p` 改成 1.0 或 2.0 時，實作必須仍然正確**——測試要涵蓋這三個值。
  若你的近似式只在 1.3 附近準，那它不是參數化的，是寫死的。

### ⚠ 定義域這件事我要你先量再實作

M5 我踩過四次同一個家族的錯：**閾值落在分布之外，規則寫了卻一次都沒命中，測試照樣全綠。**
這裡的形式是：**`R` 的查表定義域涵蓋不了實際會出現的 `R`，於是靜靜地飽和。**

M6.0 已經量過：一個 tier 4 的權重是 tier 0 的 **256 倍**。
所以「劍聖 vs 一隊民兵」的 `R` 輕易就是三位數，不是 0.5～2。

**做法**：先寫一支小程式，用 M6.0 的等效戰力掃過實際會出現的組合
（單人 vs 軍團、軍團 vs 軍團、傳奇 vs 傳奇……），**量出 `R` 的實際分布與極值**，
再據此決定定義域。**回報要附這個分布**（至少：最小值、最大值、95 百分位）。

超出定義域時**必須是明確的、可觀測的處理**（飽和並記旗標，或 `AETH_CHECK`），
**不准靜靜地夾住**。負向控制：餵一個超出定義域的 `R`，確認它真的被偵測到。

## 不打到最後一人

```
若 累計損失率 > 崩潰閾值(morale) → 潰散
```

崩潰閾值初值約 30%——**大多數戰役結束於一方崩潰，而非全滅**。
純損耗公式會產生殲滅戰，那不符合真實也不好玩。

**追擊損失（`pursuit_loss`）往往大於交戰本身**，必須進公式。
它讓「保持完整撤退」成為一種能力，而不是理所當然。

**驗收要量的**：隨機 1000 場戰役，**全滅收場的比例**。
若那個比例超過兩成，崩潰閾值就沒有發揮作用——如實回報，不要調參數把它藏起來。

## 位階門檻怎麼進公式

設計文件講得很精確，照做：

> 先用主公式算出雙方的**總損失**，再把損失**分配**給參與者時，
> 高位階個體按門檻豁免，豁免掉的部分**由低位階者吸收**。

⚠ **這就是配額守恆**，與 [`significance-fate.md`](../../design/significance-fate.md)
是同一套機制。所以：**總損失在分配前後必須完全相等**（整數，不准有捨入漏失）。

驗收：`Σ 分配後的個別損失 == 主公式算出的總損失`，**逐位元相等**，附實測。

結果是「劍聖不會被人海殺死，但他所在的部隊會被打垮。他只能全身而退，救不了軍隊。」
**這句話要能被一個測試表達**——寫那個測試。

## 一旬涵蓋的其他損耗

Region 回合是十天，除了交戰還有：補給消耗（圍城方更大）、疾病（長期圍城的主要殺手）、
逃兵（士氣低／補給差／遠離家鄉時上升）、季節（冬季行軍與駐紮）。

這幾項讓「久攻不下」自己就會付出代價，**不需要額外的計時器設計**。

## 輸出

```cpp
struct CombatResult {
    int32_t loss_a, loss_b;               // 等效戰力損失
    Outcome outcome;                      // 續戰 / A潰散 / B潰散 / 雙方脫離
    int32_t morale_delta_a, morale_delta_b;
    std::vector<ParticipantFate> named;   // 具名參與者的個別下場
};
```

`named` 的三階段判定是**下一輪 M6.4** 做的，這輪只留欄位與介面。

## 可解釋：每一項都要能寫進戰報

設計把「可解釋」列為四條硬性要求之一。所以 `CombatResult` 要能回答
「為什麼輸」——**每個修正項對結果的貢獻要可取出**，不是一個算完就丟的中間值。

不必做 UI，但要有一個結構化的分解（各修正項的乘數與它造成的損失差），
並用一個測試證明：拿掉補給劣勢後結果會翻轉，且分解裡指得出來是補給。

## 這條公式也給 AI 用

⚠ **AI 判斷「這仗打不打得贏」用的就是這一條，沒有隱藏勝率表。**
所以它必須是**公開的純函式**，不准有 AI 專用的變體或旁路。
玩家能學會的推算，AI 也只用那一套——這是策略遊戲公平感的來源。

## 驗收

| 判準 | 怎麼量 |
|---|---|
| `R` 定義域 | 附實際分布（min／max／95%），超域有明確處理 |
| `p` 真的是參數 | 1.0／1.3／2.0 三個值都正確，附三組數字 |
| 無浮點 | `grep` 不到 `double`／`std::pow`／`float` |
| 配額守恆 | 分配前後總損失**逐位元相等** |
| 不打到最後一人 | 1000 場隨機戰役的全滅比例 |
| 階差門檻 | 劍聖全身而退但部隊被打垮，**有一個測試表達這句話** |
| 可解釋 | 拿掉補給劣勢結果翻轉，分解裡指得出來 |
| AI 無旁路 | AI 路徑與玩家路徑呼叫**同一個函式**，附證據 |
| 決定性 | 同輸入同結果 |
