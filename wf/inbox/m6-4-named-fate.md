## 要同時做到的三件事

饑荒發生在某座城。玩家認識的那位雜貨店老闆娘住在那裡。

| 做法 | 為什麼不行 |
|---|---|
| 只算統計 | 老闆娘的生死沒有答案，玩家感覺不到任何事 |
| 逐一模擬每個人 | 十萬人各擲一次骰，成本無法接受，大部分結果沒人看 |
| 讓具名角色免疫 | 世界失去重量，玩家認識誰誰就不死 |

## 三階段演算法

```
階段 1  對 Cohort 算出總量          → 平民 Cohort 損失 1200 人（12%）
階段 2  對 Cohort 內的具名成員逐一擲判 → 老闆娘：倖存 / 死亡 / 重傷 / 流離
階段 3  用階段 2 的結果回填配額       → 無名成員損失 = 1200 − 具名實際死亡數
```

⚠ **階段 1 永遠先跑，而且它的結果是權威的。**
這與「數值歸 Region」完全同構——總量由高層決定，個體只是在總量之內分配。

### 階段 2 的修正項全部要**可解釋**

能寫進敘事的才准進公式：

| 修正項 | 方向 | 敘事 |
|---|---|---|
| 地位（貴族、官員） | ↓ | 「城主的糧倉先開給了自己人」 |
| 財富、存糧 | ↓ | 「她鋪子後頭還藏著半袋麥」 |
| 與玩家的關係深度 | ↓ | 玩家在乎的角色有倖存偏袒 |
| 職業風險（醫者、士兵） | ↕ | 瘟疫中醫者死亡率更高 |
| 年齡、健康、特質 | ↕ | 老人與孩童在饑荒中更脆弱 |
| 所在分區 | ↕ | 貧民區的損失率高於商業區 |

`outcome` **不是生死二元**，是一個分布：

```
倖存無恙 / 倖存但重傷 / 倖存但失去財產 / 流離（遷往他處）/ 死亡
```

「流離」特別有用：角色離開這座城但仍活著，日後可能在別處重逢。**不要省掉它。**

⚠ **倖存偏袒是刻意的，但不是免疫。** 被 mark 的角色死亡機率明顯低於平均，
**卻永遠 > 0**。偏袒係數是難度選項，硬核模式下趨近 1。
驗收：跑 10000 次，被 mark 角色的死亡次數必須 **> 0**，且明顯 < 未 mark 的。附兩個數字。

## 階段 3：配額守恆是硬性要求

> **具名成員的判定結果必須從 Cohort 的配額中扣抵。**

三個理由，第二個是玩法上的：

1. **統計層與個體層不能有兩個真相**
2. ⚠ **防刷**。若具名角色的倖存是「額外」的，玩家就有動機**大量 mark 人來降低總損失**。
   守恆讓 mark **不改變總量，只改變誰承受**。
3. **歸約一致**。Cohort 的損失最終要歸約回 Region 的人口數字，不守恆就會漂移。

**溢出情況也要處理**：若具名成員的死亡數已超過配額，就**不再對無名成員扣損**，
並記一則「這場災難特別針對了有頭有臉的人」的敘事。

### 驗收（防刷是這輪最重要的一條）

同一個災難事件，跑兩次：**mark 0 個角色** vs **mark 50 個角色**。
**Cohort 的總損失必須完全相同**（逐位元）。
若不同，玩家就有一條刷法。附兩個實測總損失。

## ⚠ 無偏性：玩家在不在場不影響命運分布

這是 M4 欠下來的那條。Site 被卸載期間發生的饑荒走**完全同一套演算法**：

- 階段 1 由 Region 層算（它本來就一直在跑）
- 階段 2 在**重載時**才對具名成員補擲（具名清單在持久層裡）
- 階段 3 自動成立，因為階段 1 的總量早記在 Region 上

**所以不會出現「常常進城的玩家，他認識的人比較容易活」這種漏洞。**

**判準**（同 [`event-scaling.md`](../../design/event-scaling.md) 的期望值一致）：

```
E[某具名角色的死亡率 | 玩家在場] ≈ E[同一角色 | 卸載後重載補算]
```

跑足夠多次（≥ 1000），相對誤差 < 5%。**兩條路徑都要真的被執行到**——
附兩條路徑各自的執行次數。⚠ **唯一容許的差別是時序**，不是分布。

## 反向：個體事件如何影響統計

上面是「統計 → 個體」，反方向也要能走：

- 玩家救了某位具名角色 → 該角色移出死亡配額 → **配額轉嫁給無名成員**
- 玩家開倉賑災 → 影響的是**階段 1 的 Cohort 損失率**，不是階段 2 的個體修正

⚠ **玩家的干預必須作用在階段 1**，這樣它才會如實反映到 Region 的人口數字上。
只改階段 2 的話，玩家會覺得「我救了她」但城市人口毫無變化——**那是設計錯誤**。
驗收：開倉賑災後，Region 的人口數字必須真的變好，附前後兩個數字。

## 決定性

- RNG 用注入的 `mt19937_64`，種子 `hash(event_id, cohort_id, entity_uid)`
- ⚠ **具名成員的擲判順序固定**（依 `entity_uid` 排序），**不依賴容器迭代順序**
- 負向控制：改成依 `unordered_map` 的迭代順序擲判 → 決定性測試要紅

## 敘事產出

每個具名成員的判定都產生一則**事件**——這是玩家實際看到的東西：

```
[饑荒·第 3 旬]  石橋鎮
  平民損失 1197 人（12%）
  ▸ 雜貨店的瑪莎 倖存，但鋪子已空
  ▸ 老兵葛倫 死於饑荒
```

**無名的部分是一行數字，具名的部分是一行故事。這正是這套機制存在的理由。**
事件要能持久化（既有機制），**顯示 UI 是 M6.6，這輪不做**。

## 驗收

| 判準 | 怎麼量 |
|---|---|
| 防刷 | mark 0 個 vs mark 50 個，總損失逐位元相同 |
| 偏袒不是免疫 | 被 mark 者 10000 次的死亡次數 > 0 且明顯較低，附兩數 |
| 配額守恆 | `具名死亡 + 無名死亡 == 階段1總量`，逐位元 |
| 溢出處理 | 具名死亡超過配額時無名不再扣損，附案例 |
| 無偏性 | 在場 vs 重載補算，相對誤差 < 5%，附兩條路徑執行次數 |
| 干預作用在階段 1 | 賑災後 Region 人口真的變好，附前後數字 |
| 決定性 | 擲判順序固定；負向控制紅了 |
| `outcome` 五種都出現 | 附五種各自的命中計數 |

### ⚠ 三個一定要避開的假通過

1. **空的 Cohort 必然守恆。** 沒有具名成員時 `0 + 1200 == 1200` 恆真，什麼都沒證明。
   **先確認具名成員真的存在、且真的有人死了**，回報附計數。
2. **無偏性測試若有一條路徑沒跑到，就是假通過。** 附兩條路徑的執行次數。
3. **五種 `outcome` 若有一種從沒出現**，那條規則等於不存在——M5 踩過四次同一家族。
