## Blocker：分桶等於沒做

你貼的磁碟佈局讓我停下來驗算：

```
10/1000100000000000.bin      Region
20/2000100400700000.bin      Site
30/3000100400703009.bin      Local
```

前兩碼是 `level` + `region_id` 的高 4 bits。而世界只有 **3～5 個 Region**，
所以 `region_id` 的高 4 bits **恆為 0**。我窮舉驗過：

| 層 | 全世界用到的桶 |
|---|---|
| Region | `10/` |
| Site | `20/` |
| Local | `30/` |

**整個世界只有三個桶。兩億個 Local zone 全部落進 `30/`。**

### 這是我的錯，不是你的

「hex 前兩碼分桶」是 `zone-save.md` 白紙黑字寫的，你照做完全正確。

但那條規則是我從 medps 抄來的——**medps 的 key 是零語意流水號，高位會變**。
aetheria 刻意改成結構化 key，高位是 `level` + `region_id`。
**我抄了結論，沒有重新推導它依賴的前提**，而 zone 定址正好是我文件裡
標成「刻意不同於 medps」的那一條。繼承來的東西，前提被改掉了就必須重驗——
這次是我自己違反了這條。

### 裁定

桶名取 key 經過一次**位元混合**（splitmix64 finalizer 之類）後的 2 個 hex 碼，
**256 個桶**。檔名仍是完整 16 碼 hex key，所以照 key 找檔、`ls` 一個桶看內容都不受影響。

256 個桶對照設計自己寫的痛點門檻（「數萬個檔案」）綽綽有餘：
實際檔案數受成長軸不變量約束，只隨**已造訪** zone 數成長，不隨世界大小成長。

已寫進 [`design/zone-save.md`](../../design/zone-save.md) 的新小節。
