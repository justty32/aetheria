## 兩件事，第二件比第一件重要得多

### 一、Site payload 進版號

新增的 Site 持久欄位（治安四因子、`PersistentNamedNpc.missing`、
`PersistentDungeon.cleared/depth`）改變了位元流，**必須升版**。
目前全域已到 v16（M6.4 的 `NamedFateLedger`）。

照 [`zone-save-history.md`](../../design/zone-save-history.md) 的既有政策：
**一律不做遷移**，舊檔大聲拒讀，不要靜默讀壞。
⚠ 但**「拒讀」與「讀成預設值」是兩件事**，要有測試分得出來。

### 二、⚠ 世界雜湊涵蓋不到新欄位 —— 這是偵測力的洞

**正規化 world hash 是所有往返測試的最終判準。**
若它算不到某個欄位，那個欄位的存檔漏失**不會讓任何測試變紅**。

這正是 [`verification-detection-power.md`](../../design/verification-detection-power.md)
說的「一個『通過』何時才算通過」——**測試綠燈但偵測不到，等於沒測**。

M6.2b 已經示範過正確做法：它把外交狀態納入正規化雜湊，
並用「只把積怨寫成 0」的注入證明雜湊真的抓得到（`9423178396657630806 → 7220728238384060368`）。
**這輪照那個做，四個新欄位各做一次。**

## 驗收

| 判準 | 怎麼量 |
|---|---|
| 版號升到 v17 | 舊 v16 Site 檔**大聲拒讀**，不是讀成預設值 |
| 拒讀 ≠ 預設 | 兩者要有可觀測的區別，附證據 |
| 治安四因子進雜湊 | 逐一改動 → 雜湊改變，附**四組前後雜湊** |
| `missing` 進雜湊 | 翻轉 → 雜湊改變，附前後雜湊 |
| `cleared` 進雜湊 | 同上 |
| `depth` 進雜湊 | 同上 |
| 冷往返 | 從檔案解碼，正規化雜湊相同（**不是 byte 相等**） |
| 決定性 | 同輸入同雜湊 |

⚠ **每個欄位都要各自有一組前後雜湊。** 「全部一起改，雜湊變了」不算——
那證明不了每一個都被算進去了（漏掉一個照樣會變）。
這與 M5 踩過四次的「規則寫了但一次都沒命中」是同一個家族。

## 負向控制

**逐一**把每個新欄位從雜湊計算中拿掉（一次一個），
確認對應的「該欄位改動 → 雜湊改變」測試變紅。
⚠ **六個欄位就要六次注入**，不要只做一次代表全部。
每次都附紅的雜湊值。

若你認為六次太囉嗦，**那正是重點**：M6.2b 只驗了積怨一個分量就足以抓到漏寫，
是因為它挑了**最慢、最不容易被別的測試抓到**的那個。
這裡沒有哪個特別慢，所以只能逐一。

## 順帶檢查一件事

M6.6b 為了讓測試綠，更新了三個寫死的 Region tile hash 基準
（`8963508752675768512 / 14515705340403023595 / 3836747774080975080`），
理由是歸約新增第五列必然改變雜湊——**這個理由成立**。

但請確認一件事並寫進回報：**那三個基準是「必然會隨資料改變」的值，
還是「本來就該恆定」的值？** 若是前者，它們不該寫死成常數，
應該改成斷言關係（同 M5.8 的裁定：斷言關係而非當下值）。
⚠ 這是判斷題，我要你的判斷，不要直接改。
