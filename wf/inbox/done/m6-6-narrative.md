## 兩件事

### 一、湧現任務：從世界狀態讀出需求

⚠ **不是「隨機組合模板」，是從世界的實際狀態讀出真實需求**：

| 世界狀態 | 長出的任務 |
|---|---|
| 某城 `food_yield` < 需求 | 運糧 |
| 某格治安低 | 清剿盜匪 |
| 某具名 NPC 失蹤 | 尋人 |
| 某勢力積怨高且國力接近 | 戰前情報 |
| 地城 `cleared == false` 且深 | 探索 |

**因為需求是真的，完成任務會真的改變世界狀態**——
運糧真的補上糧食缺口，清剿真的提高治安。
⚠ 而且**必須走既有的歸約通道**（`interface-world-mid.md`），
不准另開一條「任務專用」的世界狀態寫入路徑。這條是硬性的。

**驗收**：完成一個運糧任務後，該城的糧食數字**真的變好**，附前後兩個數字；
且那個變化是經由歸約通道發生的（附證據，例如歸約量的計數）。

**負向控制**：把需求偵測改成「隨機挑一個任務」→
「完成任務改變世界狀態」的測試必須紅（因為需求是假的，改的地方對不上）。

### 二、Godot 端的敘事顯示

core 已經在產事件了，這輪把它接到畫面上：

- 事件列表／戰報面板（`poll_events()` 既有通道，**不要新開跨界 API**）
- ⚠ **所有面向玩家的文字走 i18n key，不寫死字串**
- 填空模板用**具名參數**而非位置參數——中文與日文語序不同，
  位置參數在翻譯時會錯位

⚠ **Godot 端不准持有玩法狀態**（`tech-stack.md` 鐵律）。
自我檢查法：把場景整個 free 掉再從 core 重建，畫面必須完全一致。
**寫一個測試或一段可重現的手順證明這件事**，不要只是宣稱。

`godot/` 沒有自動測試，所以這部分的驗收是：
`--check-only` 語法檢查通過 + headless 跑得起來 + **截圖或文字 dump**，
證明事件真的顯示出來了。**沒有證據就是沒做完。**

## 命運判定的敘事輸出

`significance-fate.md` 指定了輸出長相：

```
[饑荒·第 3 旬]  石橋鎮
  平民損失 1197 人（12%）
  ▸ 雜貨店的瑪莎 倖存，但鋪子已空
  ▸ 老兵葛倫 死於饑荒
```

**無名的部分是一行數字，具名的部分是一行故事。**
三階段判定本身是 M6.4 在做，**這輪只做模板與呈現**，
用假資料驅動即可，但模板要能直接接上 M6.4 的真實輸出。

## ⚠ 設計文件自己記了這個賭注可能會輸

> 程序生成的敘事容易「有結構但無靈魂」。系統能保證「這條古道通往那座廢墟」
> 是自洽的，但保證不了玩家會**在意**。

**所以這輪回報要有一段你自己的判斷**：把湧現任務實際跑出來之後，
**它們讀起來像不像真的有意義**，還是像「殺 10 隻狼換錢」。
⚠ 這是主觀判斷，我要的就是主觀判斷——如實寫，不要客套。
這是 M5 留下的「能動但不像真的」那條的第一次正面檢驗。

## 驗收

| 判準 | 怎麼量 |
|---|---|
| 需求是真的 | 完成任務後世界狀態真的變好，附前後數字 |
| 走既有歸約通道 | 附歸約量計數，沒有任務專用寫入路徑 |
| 五種湧現任務都長得出來 | 附五種各自的生成計數，**任何一種是 0 就是有問題** |
| 事件真的顯示 | headless dump 或截圖 |
| Godot 無玩法狀態 | free 場景後重建，畫面一致 |
| i18n | `grep` 不到寫死的中文字串在 `godot/` 的邏輯裡 |
| 模板用具名參數 | 附一個換語序不會錯位的證據 |
| 負向控制 | 需求改成隨機後測試紅 |
