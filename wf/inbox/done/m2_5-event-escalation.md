## 這輪：M2 的最後一塊

`interface-world-mid.md`：

> 歸約量表處理的是**連續量**。但有些事不是量的變化，而是離散的、當下就該讓世界知道的：
> **城破了、領主死了、神器被挖出來了。**
> Site 內發生的事件，若重要性 ≥ `Region` 級，**立即**升級成 Region 事件並改變 Region 狀態，
> 不等每旬的數值歸約。
>
> **兩條通道加起來才是完整的 L2 → L1 界面。** 只有歸約通道的話，
> 玩家會發現「城池已經淪陷，但外面的世界要到下個旬才反應過來」——**那是設計錯誤。**

### 這輪的核心風險：「不算兩次」在這裡更難

設計那句很短，但它是這輪最容易錯的地方：

> 升級的事件同樣要走「不算兩次」規則：**升級事件已經改過的量，該旬的歸約不得重複計入。**

`has_live_site` 那條是「二選一」——Site 在場就整個跳過 Region 公式，界線很乾淨。
**這條不是**：同一旬裡，某個量可能**一部分由升級事件即時改過、一部分還要靠歸約補**。

⚠ 所以要有**負向控制**：造一個「事件升級改了某個量、同一旬又走歸約」的情境，
證明那個量**沒有被加兩次**。只證「結果看起來對」不夠——
如果事件的效果剛好是 0 或歸約剛好沒動到同一個量，那個測試什麼也沒證。
**先確認兩條路徑真的都碰到同一個量**，再證它只算了一次。

## 範圍

1. **重要性等級接上**：Site 事件的重要性沿用 `significance.md` 的同一套等級，
   **不要另立一套詞彙**（跟 LOD 沿用 observer 的等級是同一個原則）。
2. **升級路徑**：重要性 ≥ `Region` → 立即改 Region 狀態，不等旬末。
3. **不算兩次**：升級改過的量，該旬歸約不得重複計入。
4. **一個真實的例子就夠**：例如「城破 → 立即改 `tile.owner`」。
   ⚠ **不要做事件系統**（`events.md` 的信箱、聚合、跨層面孔那些是後面的里程碑），
   這輪只做**界面上的那一段**：Site 事件如何越級改到 Region。
