## 為什麼是現在

Local 到現在**沒有尋路**。而 M5.17 評估 libtcod 的結論是：

> FOV／BSP／噪聲／RNG／呈現全部不借，**唯一值得借的是 Dijkstra map 的概念**。

⚠ **借概念，不借程式碼**——libtcod 是查格的，我們的牆是邊。

## 要做的

Local 上的尋路，**擋路判斷必須查邊**（跟 FOV 同一條線）：

- 牆擋、關著的門要先開、上鎖的門擋
- 地面成本來自 `GroundDef::move_cost`
- **垂直層**：樓梯是「某格的 z 方向可通行」，尋路要能上下層（M5.19 在做那一層，
  ⚠ **本輪只要介面接得上，不要依賴它的實作細節**）

### ⚠ 未載入時必須退化，不能報錯

照 [`lowmap-streaming.md`](../../design/lowmap-streaming.md) 的表：

| 情況 | 退化 |
|---|---|
| 尋路目標在未載入的 zone | **用上層 Site 的粗粒度路徑規劃，進入後再細算** |
| 完全沒載入的遠方 | 回「未知」，**不是錯誤** |

## 驗收

| 判準 | 怎麼量 |
|---|---|
| **邊擋路** | 兩個可走格中間有牆 → 路徑必須繞。⚠ **把判斷改成查格，測試必須紅**（同 FOV 那條） |
| 門 | 關著的門路徑可過（標記需開門）；上鎖的門必須繞 |
| 退化 | 目標在未載入 zone → 回粗粒度路徑或「未知」，**不 throw、不當機** |
| 無路可走 | 回「無路」，不是空路徑也不是當機——**兩者要分得開** |
| 最佳性 | 同一張圖上路徑成本 ≤ 任何手工構造的替代路徑 |
| 預算 | 暖機後 min-of-5，附「展開了幾格、路徑幾步」的計數。**計數 0 不算通過** |
| 決定性 | 同輸入同一條路徑（**同成本時的 tie-break 要穩定**，不要依 map 迭代順序） |

### 負向控制

- 查邊改查格 → 必須紅，寫出路徑長度從多少變多少
- ⚠ 別用**沒有牆的空圖**測「邊擋路」——那是空的層必然通過
