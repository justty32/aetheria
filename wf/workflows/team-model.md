# team-model — 誰來做：角色三層、聰明度分級、選人判準

← [WORKFLOWS](../WORKFLOWS.md)｜[INDEX](../INDEX.md)｜**本專案的團隊制與波節奏 → [TEAM](team-model/TEAM.md)**

本檔記**誰來做**——分幾層角色、每層派哪一級的模型、按什麼順序選人。**怎麼做**在別處：派工與驗收見 [dispatch](dispatch/README.md)，限流與並行見 [dispatch/OPS-NOTES](dispatch/OPS-NOTES.md)，通訊見 [inbox](inbox/README.md)。aetheria 實際採用的角色（調度長／波管家／sonnet 雜務手／codex sol・terra）與成本前提是使用者 2026-08-27 的裁定，在 [TEAM](team-model/TEAM.md)；本檔是通則。

**何時用**：要開一個 agent 團隊、要決定某一層派哪級模型、要按用途分角色。
**何時不用**：只有一條線、一兩個檔的小改（見 [dispatch](dispatch/README.md) 的「何時不用」）；只是要送一則情報 → [inbox](inbox/README.md)。

## Done when

- 下方分級表與消耗速度表已按**你自己的模型清單**填完。
- 這一輪要開的每一層都**指名了誰**——頂層、領導、工人各自是哪一格。

## 一、角色三層

### 頂層 agent（使用者直接面對的那一個）

職責四件：接收指令、開 agent 團隊、傳達指令、**協調使用者自己也會用到的資源**（鍵盤滑鼠螢幕，乃至 CPU、硬碟、網路）。**資源授權的源頭是使用者**——頂層只是代為分配，**不能自己創造授權**。

頂層只轉達與調度，**比領導笨是正常的**：計畫不在頂層做。

對使用者說話要**適合使用者理解**：初次出現的東西先用白話講一句。**預設不必翻譯**；只有使用者說今天不想動腦才逐項翻，翻譯本身吃太多 context 時，改成直接指出**該先看哪些檔**。

頂層通常可以有**自己的私人輔助者**（查資料、盤點），不必事事經過領導。輔助者**不算團隊 headcount**，數量由使用者指定，**沒指定就默認兩個**。

平時**不掛信箱醒鐘**、不逐則讀信——那是領導（波管家）的事。**例外**：團隊裡有外部 agent 要直接找頂層時，頂層也要盯自己的信箱（見第七節）。

### 團隊領導（＝計畫制定者）

職責：把目標拆成計畫、寫交接書、派工、監看、核驗、收線。

負擔重（計畫＋指揮＋匯報），所以**模型下限比工人高**——這一層要先訂一個下限級別，不從便宜格裡挑。**若「制定計畫」被分出去給某個成員，領導只剩指揮與匯報，就可以降一級。**

**跨體系的 agent 不建議當領導**：即使有 inbox，和頂層溝通仍然有成本。

兩條實務提醒：交接書的**範圍詞會被線遞移展開**，範圍要用排除法寫死、**件數 gate 與容量 gate 並列**（見 [dispatch](dispatch/README.md)）；領導自己 context 吃緊時**寫 state 檔交棒**，不硬撐。

### 工人

依任務難度／內容，加上**使用者給的 headcount**，配便宜模型。工人自己再開子 agent **我們不管**——它在那一層就是領導；我們只告訴它**那邊能用多少資源**。

## 三、token 消耗速度

兩條規則：

- **同一廠商內**通常**與聰明度成正比**——越聰明越貴。
- **不同廠商的同級模型可以差到兩級**，所以這張表**要自己實測填**，不能照抄別人的。

重點是推導出來的那一格：**「聰明度高、消耗速度低」的那一格就是性價比之神，工人層大量用它。**

| 模型 | 聰明度 | 消耗速度 | 結論 |
|---|---|---|---|
| gpt-sol | A | C（A 下移兩級） | **性價比之神；工人層主力** |
| gpt-terra、gpt-luna | C／D | E／F（同規則下移兩級） | 便宜到掉出 Claude 的表 |
| Fable／Opus／Sonnet | 見上表 | 與聰明度同級 | Claude 系列，成正比 |

> 上表同樣是 **2026/09/02 由 justty32 給出的個人判斷**：Claude 系列消耗與聰明度成正比，GPT 系列整體下移兩級；本專案的帳單前提（Claude 按 token 稀缺、codex 月訂閱吃到飽）在 [TEAM](team-model/TEAM.md)。

## 四、選人判準（按序看這六項）

1. **任務難度／內容**——決定聰明度下限。
2. **使用者給的 headcount**——外生的上限，**不自己加碼**。
3. **token 消耗速度**——所以工人層大量用便宜模型，貴的留給真的需要的那幾件。
4. **溝通方便與否**——跨體系即使有 inbox 仍有成本，所以**領導層不建議跨體系模型**。
5. **管理上限**——**開太多領導不好管**；寧可少開領導、把量壓在工人層。
6. **時程**——用「產出速度 × 繞圈數 × 模型癖好」反推每段派誰、排多久，算法見 [speed](team-model/speed.md)。

## 六、context 管理

每層管自己下級的 context——管得好就是清雜訊，直接提升決策品質。五條規則見 [context](team-model/context.md)。

## 七、信箱與醒鐘

本專案兩個角色**共用**一個收件匣 `inbox/`（靠收件人欄辨識，見 [inbox](inbox/README.md)），未升級 kernel 的五通道；與 codex 的即時通道是 `.codex-inbox/`（[dispatch/CODEX-PROTOCOL](dispatch/CODEX-PROTOCOL.md)）。醒鐘規矩在 [TEAM](team-model/TEAM.md)：調度長每波只醒兩次，**所有信件、回報、`.ask` 的原文只進管家的 context**。只有一條是本檔的：**領導上呈時重寫標題、帶自己的判斷，不是原文轉貼。**
