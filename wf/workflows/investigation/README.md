# investigation — 調查工作流

← [WORKFLOWS.md](../../WORKFLOWS.md)｜[INDEX](../../INDEX.md)

**什麼時候用**：使用者說「**看看現在狀況**」「**這個功能有做嗎**」「**差距在哪**」
「解讀某個外部系統／評估可行性」——也就是**只要知道現況、還不要動手改**的時候。

> 與別的工作流的界線：
> **investigation**＝盤點現況與差距，**不改 `core/`／`bridge/`／`godot/`**，產出一份報告；
> **spec**＝討論出方案；**plan**＝展開成動工計畫；**feature-dev**＝真的動手。
> 調查報告**不寫解決方案**——最多列「牽扯到哪些部份」，方案留給下一棒。

## 流程

1. **把問題寫成幾條可判定的提問**（能用「是／否／部分 + 佐證位置」回答的）。
   模糊的題目會換來模糊的報告。
2. **先讀設計文件、再讀程式碼**——本專案兩者常有落差，
   **落差本身就是調查結果**（文件說有、程式碼沒有，要寫進報告）。
3. **fan-out**：把彼此獨立的提問分給 subagent（簡單的盤點用 sonnet + `Explore`），
   每個 agent 一個主題、要求**每點附 `檔案:行號`**、**找不到就說找不到**。
4. **關鍵結論自己覆核**：轉述 agent 的結果之前，至少自己 grep 一次它的核心斷言。
   → 這條的由來見 [OPS-VERIFY.md](../../OPS-VERIFY.md)。
5. **寫報告進本資料夾**（一主題一檔，命名 `<主題>-status.md`，上限 8 KB），
   並在下面的清單加一列。
6. 報告若揭出「會在未來咬人」的東西 → 同時記進 [KNOWN-TRAPS.md](../../KNOWN-TRAPS.md)；
   卡在使用者裁定的 → [WAIT_USER.md](../../WAIT_USER.md)。

## 報告的固定骨架

每份報告照這五節寫，順序不變：

| 節 | 內容 |
|---|---|
| **問題** | 使用者原話 + 拆出的可判定提問 |
| **結論** | 一句話回答「做了沒」。做了幾成就寫幾成，**不四捨五入成「有」** |
| **現況** | 已經有的東西（附 `檔案:行號`），含**設計文件說了但沒實作**的 |
| **差距** | 缺什麼、被什麼擋住，一項一列 |
| **牽扯到的部份** | 動這件事會碰到哪些檔案／測試／存檔版本／已建立的判準 |

⚠ **量到的才寫**：檔案數、測試數、寫死常數的個數這類數字一律實際數過再寫，
不要寫「大量」「不少」。
