# 一份狀態，只由一套規則改動

[本層入口](README.md)｜← [三層模擬契約](world-simulation-contracts.md)｜[原則](../../../../design/principles.md)｜[用詞](../../../../design/glossary.md)

## 地圖主場與系統寫入權是兩件事

「這件事目前在 Local 詳算」不代表人物、生活、AI、戰鬥四個模組都能各存一份人物血量。地圖主場決定在哪個解析度推進；下表決定哪套領域規則可以驗證並改動。AI、UI、任務與腳本都只能查詢或提出命令。

這是設計上的唯一寫入責任，不要求所有欄位塞進一個物件。資料可按 zone 儲存，各系統仍透過授權介面與主場提交線改動。

13 類狀態的寫入責任（狀態／唯一負責的規則／其他系統如何使用）已抽到 [world-state-ownership.json](world-state-ownership.json)。

## 一次跨系統操作

以「製作一把劍」為例：工作規則取得預約 → 物資帳本扣材料 → 力量／製作規則決定合規品質 → 物品規則產生實例或批次 → 帳本記入庫與保管 → 人物獲得工作經歷 → 歷史記已發生的事。任何步驟失敗，要依事先定好的提交／取消規則處理，不留下已扣材料又無工作紀錄的半套結果。

**批次不等於逐件物品**：普通同質資源可以批次 ID＋數量存在。只有展開成具體物品時才發個體 ID；從批次拆出必扣量，併回要符合品質／來源等可合併條件並註銷原引用。具名物或有持久個別經歷的物品不任意併回。精確政策在物品系統細化。

## 各主場層如何使用

粗算時，健康與生產規則操作人群統計；詳算時，同一領域規則以個人與現場工作作輸入，扣抵高層交出的配額。具體公式可以不同，但結果要符合守恆與校準契約。

人物的所屬地點、旅行區間與當前主場必須可追查；可拋棄的是已明定可重建的局部姿態、路徑或暫態格位置，不能把「人究竟在哪裡」整件事丟掉。普通物、個人持有物、角色控制資料也必須明確區分。

驗收時查「誰真的寫入」，不只查資料型別存在；任一系統新增直接改別領域容器的旁路，都要重新檢視此表與提交流程。
