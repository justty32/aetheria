# M10 裁定點 — 要使用者拍板的事與建議預設值

← [runtime-injection.md](runtime-injection.md)（總覽）｜[WAIT_USER](../../WAIT_USER.md)

> 每條給**建議預設值**。標「不擋路」的：計畫先照建議做，之後改裁定只影響後續輪次。
> 標「擋 Rx」的：走到那一輪之前要拍板。

## 1. 注入的粒度 — 不擋路

**建議：最小單位是「一筆 def」或「一個實體」；「一個文明」是組合包。**
組合包＝多筆注入在**同一個回合尾端**一起結算（def 先於引用它的實體）。
這讓「只加一個角色」「只加一種地形」天然成立，文明包只是批次。

## 2. 注入的來源 — ✅ 已定（使用者 2026-08-27：「隨你」）

**定案：先做外部檔案，遊戲內 UI 之後。**
形式：把 TOML 片段丟進 `saves/<世界>/inject/`，下個回合尾端被吸收、
記入歷史日誌後移到 `inject/done/`。與 DF 改 raws 的心智模型一致，
不用先做任何 UI 就能端到端驗證整條注入鏈。

## 3. 新勢力怎麼出現 — ✅ 已定方向（使用者 2026-08-27）

使用者原話：「想想看那些奇幻小說，一個新勢力怎麼出現的？**分裂、小部族成長而來、開拓**」。

**落法：出現方式（origin）本身是資料，不是 enum**（原則五管到底）。
`data/faction_origins.toml` 定義各 origin 的條件與效果；M10 內先實作**開拓**
（無主地生成起始聚落——最小、不動既有實體）；**分裂**（割地＋繼承外交立場＋需要
一個帶頭的具名人物）與**小部族成長**（中立聚落升格）都需要人物實體與敘事掛鉤，
排 M10.6a 之後成獨立輪（M11 候選）。無主地不夠時注入失敗、記入日誌——失敗也是歷史。

## 4. 世界歷史日誌可不可編輯 — 不擋路

**建議：append-only。「編輯」＝截斷到某一點＋重放成一個新世界（另存）。**
不支援原地改寫——原地改寫會讓「重放一致」的判準無從定義。
R3 先做 append-only；截斷重放若要做，是 M10 之後的獨立輪。

## 5. root 的成長軸擱置 — 不擋路，但要開始量

維持你原本的擱置裁定。但注入會讓 root 級結構（勢力表、歷史日誌）**真的持續變大**，
所以 R3 起在整合輪的驗收裡**量測並記錄** root 大小，痛了再解除擱置——
量測不是實作，不違反擱置。

## 6. 計畫直接採用的解讀（已被你 2026-08-26 的裁定涵蓋，不再問）

- **[definitions.md](../../../design/rules/definitions.md) 的「def 不進存檔」作廢**——
  DF 模型（存檔自帶 raws）正是它的反面。計畫會修訂該文件並留下改判理由。
- **Ruleset「載入後不可變」改成「載入後只可追加、只在回合尾端」**——
  不可刪、不可改既有 def（下標穩定性與快取都靠這條保住）。
  執行期要「改」一筆 def？那是 M10 之後的事，先不做。
- **同一個世界可掛多個角色檔**——裁定原文「世界是一個存檔，人物是一個存檔」的直接推論。

## 7. 要不要換 SQLite？（使用者 2026-08-27 提問）— 裁定：先不換，但把換的路留死

使用者的擔心：新世界初始注入很多、或 `saves/<世界>/` 內容愈來愈多。判斷：

- **注入量不是問題**：注入走 append-only 日誌，一萬筆也只是順序寫；
  世界建立時的「初始注入」更該直接進**基底 raws**（見裁定#8），根本不進日誌。
- **SQLite 真正買到的是跨檔案交易與崩潰恢復**——這正是審稿點名的缺口。
  但 M10.3 用 journal-first＋commit marker（event sourcing 標準解）就能補上，成本小得多。
- **代價**：raws 與 `inject/` 的「玩家用文字編輯器就能改」是功能（DF 精神），進 DB 就沒了；
  世界雜湊、存檔 diff、既有 256 桶結構全要重做。
- **定案**：檔案樹保留；`ZoneStore` 已是窄介面（原則九），SQLite 列為**明確的備援後端**
  ——要換時只動 store 實作，不動任何呼叫端。M10.8 驗收時量測存檔大小／檔案數／
  載入時間寫進回報，數據說該換再換。

## 8. 基底 raws 不可變（審稿後補的計畫內裁定）

存檔的 `raws/` 在世界建立時複製、**之後永不改寫**；執行期注入的 def **只活在歷史日誌**，
載入＝載基底 raws＋重放日誌。理由：若把注入也寫回 raws，重放時同一 def 會套用兩次、
撞全域 id 唯一性檢查（`toml_read.h:108-116`）。這也順帶免掉「改寫 `faction_count`
要原子改檔」的麻煩——日誌是注入的唯一真相。

## 9. 注入覆蓋面 — ✅ 使用者 2026-08-27 裁定：「所有東西」

原話：「要可以在遊戲過程中新增的，不只是人物/文化/物品，我預期是**所有東西**都可以。」

**落法：通道做成通用的，不逐型別開工。** 日誌的 def 條目存「目標資料檔＋TOML 片段」，
影子驗證＝用**既有載入器**從基底 raws＋日誌整批重建——所以載入器認得的每一類 def
（現有 18 類＋之後資料化的兵種／AI 目標動作／建築、新增的文化／物品）
從 M10.3b 起**全部**可注入；交叉引用與完整性檢查由載入器的 fail-fast 白吃白喝，
一類都不用另寫驗證。實體類注入按種類逐輪點亮：勢力＋聚落（M10.4）、
人物＋部隊（M10.6a）、物品實例（M10.6c）。
M10.8 驗收含**全型別矩陣測試**：每一類 def 至少注入一筆、存／讀／重放三者一致——
「所有東西」不是宣稱，是一條會紅的測試。
**唯一排除在 M10 外的：Lua 劇情腳本的注入**——script 層目前與 def 零耦合
（盤點確認無任何掛鉤點），要從零設計，列 M11 首項。
